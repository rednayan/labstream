01 Purpose

What LSL is, and the problem it solves

A neuroscience experiment records from many devices at the same time. An EEG amplifier, an eye tracker, a motion capture rig, and a script that marks events all produce data. Each device has its own clock, and those clocks drift apart.

LSL gives each device one job: publish a stream. Any other machine on the network can find that stream and subscribe to it. LSL then measures the offset between the two machine clocks and corrects every timestamp it delivers.

This is the reason the library exists. Without clock correction, LSL is a socket library with service discovery. With it, data from six devices lands on one timeline.

Two objects

An outlet publishes a stream. An inlet subscribes to one. Almost every class in the codebase belongs to one side or the other. This split is the fastest way to read the source.

05 The outlet

One object that owns two thread pools

A stream_outlet_impl holds two asio::io_context objects and one thread for each. This split matters. The data context carries samples, and the service context answers discovery and time queries.

A slow discovery reply therefore cannot delay a sample, and a busy data feed cannot make the stream undiscoverable. The design isolates the real-time path from the control path.

The sample pool

A factory pre-allocates samples in one slab and keeps a free list. A push takes a sample from the list, and a completed send returns it. The stream therefore does not allocate memory per sample at steady state.

The free list is a multi-producer, single-consumer queue by Dmitry Vjukov. Only one thread can call new_sample for a given factory.

Trap for a reimplementation

The query_id is std::to_string(std::hash<std::string>(query)). The result of std::hash differs between libstdc++, libc++, and MSVC.

It is an opaque round-trip token. The responder echoes it and the requester compares it with what it sent. A correct implementation must never derive or validate it.

The query language

Stream matching calls pugi::xpath_query(query).evaluate_boolean(...). This is full XPath 1.0 against the stream metadata document, not a restricted subset.

Results are cached per query string. The sign of the cached value records whether the query matched, and the magnitude records the age for eviction.

09 Sample encoding

Two formats, and only one is simple

Protocol 1.10 writes samples directly to the socket buffer. One tag byte comes first, and the channel values follow. Values are byte-swapped only when the negotiation selected the opposite byte order. 

// protocol 1.10 and later, src/sample.cpp
u8  tag    // 1 = deduced timestamp, no bytes follow
            // 2 = transmitted timestamp, f64 follows
f64 timestamp   // present only when tag = 2
... channel values  // N values, swapped if byte orders differ

A deduced timestamp carries no bytes at all. The receiver derives it from the nominal sampling rate and the position in the stream. This is how a regular stream avoids eight bytes of overhead per sample.

Protocol 1.00 is a different animal

Protocol 1.00 does not use this layout. It uses eos::portable_archive, a Boost serialization format with its own header, versioning, and float encoding.

Any reimplementation must treat 1.00 as separate work. The 1.10 codec is a few hundred lines. The 1.00 archive format is much more.

10 Clock sync

Four timestamps, NTP style

The inlet sends a time probe and the outlet answers. Four timestamps come out of one exchange. Two are taken on the inlet clock, and two on the outlet clock.

Fig. 7 — Time probe and the four timestamps 100% 
sequenceDiagram
  participant I as time_receiver (inlet)
  participant O as udp_server (outlet)

  Note over I: t0 = local clock
  I->>O: LSL:timedata + wave_id + t0
  Note over O: t1 = remote clock on arrival
  Note over O: t2 = remote clock on send
  O->>I: wave_id + t0 + t1 + t2
  Note over I: t3 = local clock on arrival
  Note over I: rtt = (t3 - t0) - (t2 - t1)
offset = ((t1 - t0) + (t2 - t3)) / 2
  Note over I: repeat the probe several times
keep the estimate with the lowest rtt

A burst of probes produces several estimates. The library keeps the one with the lowest round-trip time and discards the rest. NTP uses the same rule, because a fast exchange has less room for asymmetric delay.

Each probe carries a wave_id. The inlet ignores any reply whose wave identifier does not match the current burst. This rejects late replies from an earlier burst.

Clock sync

This stage adds the last measured offset. It refreshes that offset every 50 samples, and never more than twice per second. A reset from the connection clears the state and the jitter filter.

Jitter removal

Network delay makes arrival times uneven even when the device samples at a fixed rate. The filter fits a straight line through sample index and time with recursive least squares.

The forgetting factor is lam = 2 ^ (-1 / (srate * halftime)). An integer baseline is subtracted first, because a raw LSL timestamp is a large number and the fit needs the precision.

Useful property

This filter is deterministic for a given input sequence. The same timestamps always produce the same output. It can therefore be tested against golden values.

Monotonic clamping

This stage never lets a timestamp go backward. It returns the running maximum whenever a new value is smaller. Some recording formats require this.

Each queue is a ring buffer with a fixed capacity. When it is full, the oldest sample is dropped so the producer never blocks. One slow consumer therefore cannot stall the device or the other consumers.

The read index and the write index are padded onto separate cache lines. This removes false sharing between the producer thread and the consumer thread.

The blocking exception

The transp_sync_blocking flag reverses this policy. A push then waits for the consumer, up to the configured send timeout. A consumer that exceeds the timeout is disconnected instead of stalling the producer forever.

13 Recovery

What happens when the stream disappears

Lab networks drop out. A machine reboots, a cable moves, a laptop switches from ethernet to wifi. The inlet_connection class exists to survive these events without the application noticing.

A watchdog thread checks whether data arrived recently. When too much time passes, it starts a resolve for the same stream. The address and port can change, so the connection updates them under a reader-writer lock.

A restarted source gets a new UID. The inlet detects this, and treats the stream as a new instance. It then clears the clock offset and the jitter filter, because both describe a process that no longer exists.

Shutdown uses a separate mechanism. Every pending asynchronous operation registers with a cancellable_registry, so a close can cancel all of them and stop new ones from starting.

15 Where it is hard

The parts that resist a clean rewrite

XPath 1.0 in the query path

Stream matching runs a full XPath 1.0 query through pugixml. No Rust crate matches the same dialect and the same edge cases. This is the largest single unknown for any reimplementation.

The 1.00 archive format

Protocol 1.00 uses a Boost serialization archive. Reimplementing it means matching a header layout, a versioning scheme, and a float encoding that no specification describes.

Implementation-defined values on the wire

The query_id comes from std::hash, and the Endian-Performance header holds a benchmark result. Neither value can be compared between implementations. Both must be treated as opaque.

Behavior that no document records

The string length prefix changes width, and the rule is visible only in the code. Chunk boundary handling has produced several upstream bug reports. The code is the only specification that exists.

The core point

The core is 14,476 lines. Generating a plausible replacement is fast. Proving that the replacement is correct is the real work, and no test suite for that exists in any language today.

01 Thesis

The advantage is not speed. It is testability.

LSL moves a few hundred kilobytes per second on a local network. Rust does not make that faster. Any claim that a rewrite improves throughput describes the wrong problem.

The real advantage is structural. A rewrite can separate the protocol from the input and output. The current core cannot, and this is measurable in the source.

The TCP server parses a request inside an asio completion handler. The call getline(requeststream_, method) sits in handle_read_command_outcome, and requeststream_ is a session member.

The consequence

A parser that needs a socket needs a network to test. Network tests are slow and they fail at random. Teams then write few of them.

The core holds 14,476 lines and the test suite holds 3,174. No conformance suite exists in any language. This is the cause, not an accident.

Every decision below serves one goal. The protocol logic must run with no socket, no clock, and no thread. Then a conformance vector becomes an ordinary unit test.

02 Sans-IO core

Bytes in, bytes out, nothing else

The protocol layer takes bytes and events. It returns bytes and events. It never opens a socket, never reads a clock, and never starts a thread.

The runtime layer wraps that core. It owns the sockets and the timers, and it feeds the core. The core does not know that the runtime exists.

05 Grades of exactness

Three bars, and each applies in one place

The word exact means three different things in this project. A claim of the wrong kind either hides a real error or fails a correct implementation.

GradeApplies toAssertion
Byte-exactSample codec, header text, request linesEquality on the byte slice
Numerically boundedClock offset, dejitter outputDifference within a stated tolerance
Behaviorally equalHandshake order, recovery, backoffSame observable event sequence

A byte-exact claim for a clock estimate is wrong, because the estimate depends on network timing. A tolerance for a codec is also wrong, because it hides encoding errors.

Write the grade into the test name

Name each test after its grade. A reader then knows which bar applies without reading the assertion. This also stops a later edit from weakening a byte-exact test.

06 Float discipline

The dejitter filter can match, if the order holds

The library builds with plain IEEE semantics. No fast-math flag appears in the build configuration. Bit-exact agreement with the dejitter filter is therefore possible.

Rust does not reassociate float operations and does not contract a multiply and an add into one instruction unless the code asks for it. The risk is the code, not the compiler.

Rules for the estimator code

  1. Write each operation in the same order as the C++ source.
  2. Do not reassociate an expression to make it read better.
  3. Do not use mul_add where the source uses a separate multiply and add.
  4. Keep the integer baseline subtraction in the dejitter filter.
  5. Run the numeric tests on x86-64 and on aarch64.

The baseline subtraction matters. An LSL timestamp is a large number, and the filter needs the precision that the subtraction returns.

State this as a goal, not a promise

Bit-exact agreement is a target for the dejitter filter. Do not promise it across every platform and every compiler version. State a tolerance in the public documentation.

04 The self-test

The protocol tests the codec on every connection

This is the largest finding in M1. It changes how the rewrite gets validated.

After the answer headers, and before any real sample, the outlet sends exactly two samples (tcp_server.cpp:694-705). It builds them with assign_test_pattern(4) and then assign_test_pattern(2).

The inlet builds the same two samples locally. It reads two samples and compares each one for equality (data_receiver.cpp:276-297).

On a mismatch the inlet raises this error.

The received test-pattern samples do not match the specification.
The protocol formats are likely incompatible.

The pattern

Every test pattern sample carries the timestamp 123456.789. The channel values follow one rule (sample.cpp:356-362). 

value[k] = (k + offset) * (k is even ? 1 : -1)

The caller offset of 4 or 2 adds to a base that depends on the format. For cft_float32 the base is 0. For cft_double64 the base is 16777217.

On the wire

A capture of a stream with 8 float32 channels holds these first three samples.

05 The dead header

The server reads a header that no client sends

The client writes Data-Protocol-Version (data_receiver.cpp:183). The server compares the name against protocol-version (tcp_server.cpp:628).

The two names differ. The server therefore never reads the header that the client sends.

This claim needed an experiment. Three requests went to the pinned oracle, and each one carried a different header.

The client sendsThe server answers with
Data-Protocol-Version: 100Data-Protocol-Version: 110
Protocol-Version: 100Data-Protocol-Version: 100

The middle row settles it. Only Protocol-Version changes the negotiated version.

The naming is asymmetric. A request carries Protocol-Version. An answer carries Data-Protocol-Version, and the client reads that name (data_receiver.cpp:244).

Why this is harmless in liblsl and dangerous for us

The default value of the client version is the version from the request line. The client sends the same number in both places, so liblsl always agrees with itself.

A reimplementation that trusts the header name in the client code writes a server that negotiates differently. Nothing in the source says the header is dead.

06 String prefix

Encode and decode are deliberately different

This was an open question from the conformance plan. A string channel writes a width byte, then the length in that width, then the bytes (sample.cpp:198-214).

String lengthWidth byteLength field
0 to 2551u8
256 to 42949672954u32
Above that8u64

The encoder never writes the width 2. The decoder accepts it (sample.cpp:251).

The trap

A u16 length for a string of 300 bytes looks correct. liblsl reads it correctly. No liblsl outlet ever writes it.

A vector set must cover encode and decode separately. A round-trip test passes with a wrong encoder, because the same wrong decoder reads it back.

The length field is byte-swapped when the connection swaps order. The width byte is never swapped.

07 Chunks

The open question was the wrong question

The conformance plan listed chunk boundary semantics as an open item. It named several upstream reports that appear to concern chunk boundaries.

A chunk is not a wire unit. The stream carries no chunk header, no chunk length, and no delimiter. A reader cannot detect a chunk boundary.

A chunk decides one thing. It decides when the server calls one socket write (tcp_server.cpp:782). The server writes when a sample carries the push-through flag, or when the count reaches the chunk size.

The server picks that size in order: Max-Chunk-Length from the request, then the size configured on the outlet, then no limit (tcp_server.cpp:747-751).

What this removes from the plan

Chunk framing needs no conformance vectors, because no framing exists. The remaining question is about the inlet API and not about the wire.

04 The canonicalizer

A placeholder must assert something

An answer carries a UID that changes on every run, so a direct comparison fails for a reason that carries no meaning.

A canonicalizer replaces the value with a placeholder. That step is where a suite quietly loses coverage. A field that gets erased with no assertion is a blind spot that reads exactly like a passing test.

The rule in this crate: every placeholder carries a predicate and a reason. A lint fails a rule that breaks it, and the lint runs as its own test before any comparison uses the rules.

source-idAny textChosen by the application

A predicate of "any text" asserts nothing, so the lint demands a longer reason for it. A field that carries protocol meaning belongs in no rule at all, because a direct comparison is stronger. Byte-Order is one of those, and a test makes sure that no rule touches it.

05 The speed contest

A measured value, handled by construction

Condition 4 of the byte order negotiation compares two conversion speeds. The outlet swaps only when it is faster than the client.

Both values come from a benchmark, so both differ between machines and between runs. A transcript that recorded a middle value would replay differently on another machine.

The corpus therefore uses only the two ends. A client value of 0 loses on every machine. A client value of 10 to the twelfth wins on every machine.

The result

Any positive server value reproduces both outcomes. The replay injects 1.0, and the answer does not depend on the machine that runs the test.

This is the same idea as a predicate. A value that cannot be compared still gets an assertion, and here the assertion is the design of the case.

03 The hidden port

Discovery uses two ports, not one

The first cross-implementation run failed in one direction. A Rust inlet read from a real liblsl outlet, and a real liblsl inlet could not find a Rust outlet.

Our outlet answered every query that the capture rig sent, on every address. A trace showed why that proved nothing: liblsl sent no datagram that our socket ever saw.

The cause

multicast_port_ = pt.get("ports.MulticastPort", 16571);   // api_config.cpp:169
base_port_      = pt.get("ports.BasePort", 16572);         // api_config.cpp:170

A multicast or broadcast query goes to port 16571. That port sits outside the unicast range, which starts at 16572.

An outlet binds both. It binds one port in the range for a unicast query, and it binds 16571 for a multicast query.

Why the earlier work missed this

The capture rig sends to the range and to 127.0.0.1, so it always reached a liblsl outlet. The rig never needed the multicast port, so the specification never recorded it.

SPEC.md section 1.1 now carries the rule. A test that only ever talks to one implementation cannot find a gap like this.

04 The multicast join

The loopback carries no multicast

A second defect sat behind the first. A join names an interface by its address, and a join that names no interface lets the operating system choose.

On this machine the choice can be the loopback, and liblsl says what that means. 

netif 'lo'       (status: 1, multicast: 0, broadcast: 0)
netif 'wlp1s0'   (status: 1, multicast: 4096, broadcast: 2)
netif 'docker0'  (status: 1, multicast: 4096, broadcast: 2)

The loopback carries neither multicast nor broadcast. A resolver on this machine therefore sends only on a real interface, and an outlet joined on the loopback hears nothing.

liblsl joins each group on each interface that carries multicast. The kernel table shows both implementations doing the same thing after the correction. 

docker0 B70000E0   // 224.0.0.183
docker0 D7ACFFEF   // 239.255.172.215
wlp1s0  B70000E0
wlp1s0  D7ACFFEF
Reading the interface list

liblsl calls getifaddrs. lsl-net reads the routing table instead, which needs no unsafe code, and it falls back to the unspecified address when the table cannot be read.

05 A hang at startup

One line that never returns

The first Rust outlet printed nothing and never started. The cause was one call in the identifier generator.

A read to the end of a file works for an ordinary file. This file never ends, so the call consumes memory until something stops it.

Worth stating plainly

No conformance test finds this. It is not a protocol error. A live run found it in seconds, because the process never printed its first line.

A suite of unit tests over byte slices cannot replace running the program.

06 The estimator envelope

A bound derived from the rule, not chosen by hand

The offset estimator cannot have a golden value. Three of its four inputs come from a network, so no fixed number describes a correct answer.

The rule itself supplies a bound. liblsl keeps the probe with the lowest round-trip time, because a fast exchange leaves less room for an asymmetric delay. 

rtt    = (t3 - t0) - (t2 - t1)
offset = ((t1 - t0) + (t2 - t3)) / 2

A path that runs slower one way biases the estimate by half the difference. The kept estimate therefore carries an error of at most half its own round-trip time. 

error 0.000092941 s, bound 0.002174126 s, over 200 probes
A bound must also be useful

A test that only asserts a bound passes when the bound is enormous. This one also asserts that the bound stays below 20 ms, so a vacuous result cannot pass.

Five more tests cover the shape of the rule: a symmetric exchange recovers the offset exactly, an asymmetric one biases by half the difference, a fast exchange beats a slow one whatever order they arrive in, an answer from an earlier burst never counts, and an empty burst reports nothing.

07 A trap in the state

A stream that starts below one second never smooths

The filter stores its baseline as an unsigned integer, and it decides whether it has started by testing that value against zero. 

t0_ = static_cast<uint_fast32_t>(t0);        // the fraction is lost
bool is_initialized() const { return t0_ != 0; }

A first timestamp below 1.0 truncates to zero. The filter then reads as uninitialized on every later sample, and it rebuilds itself each time.

An LSL timestamp usually comes from a clock with a large value, so this rarely appears. A stream that starts its own clock at zero meets it at once.

Recorded, not corrected

This implementation copies the behavior, because a different answer would not match the oracle. A unit test names it so that no later reader treats it as a defect in this code.

05 Two units, one header

06 Recovery

The recovery query is not the resolve query

MeasureliblslRust

The two counts before the stop differ because they read a wall-clock moment during a live push. They are not protocol values.

Three rules from the source

channel_count='4' and name='X' and type='Y'
  and source_id='Z' and channel_format='float32'
  1. The query leaves out the nominal rate on purpose. liblsl explains why in a comment: a rate written as text and read back is often a different number, and the stream would then never be found. It leaves out the session identifier too.
  2. The result must be unique. A source identifier that is not unique would otherwise attach the inlet to the wrong stream. A result that still carries the old identifier means the source never left.
  3. A stream with no source identifier cannot be recovered at all, and liblsl warns about it at connection time.

One thread owns the connection for its whole life, so no socket passes between threads. The watchdog is not a separate timer: a source that stopped without closing looks exactly like a quiet one, and the 15 second threshold is what separates them.
